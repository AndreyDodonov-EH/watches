# Companion app hand-off — controlling the watch from a web page (BLE + SoftAP)

_Written 2026-08-20 after Phase 3 (liquid face live on the board, 40 fps). Temporary working doc; fold the
decisions into STATUS.md as they land._

## Goal

One static web app ("companion") with a **transport abstraction**; the UI never knows how it talks to the
watch. Interface, roughly:

```ts
interface WatchTransport {
  connect(): Promise<void>; disconnect(): Promise<void>;
  getParams(): Promise<Params>;                 // full struct
  setParams(patch: Partial<Params>): Promise<void>;
  setTime(epochMs: number, tzOffsetMin: number): Promise<void>;
  listPresets(): Promise<string[]>; loadPreset(n: string): Promise<void>; savePreset(n: string): Promise<void>;
  subscribeTelemetry(cb: (t: Telemetry) => void): () => void;   // fps, tilt, fill, heap, battery
  readonly status: 'disconnected' | 'connecting' | 'connected' | 'error'; onStatus: (s) => void;
}
```

Implementations, in the order they should be built (see "Where to start"):

| # | Transport | Where the app runs | Platforms | Firmware work |
|---|---|---|---|---|
| 0 | **Web Serial** (exists for IMU stream) | `sim/` dev server / hosted | Chrome desktop + Android (USB-OTG) | none — `p…` line protocol already there |
| 1 | **Web Bluetooth → GATT** | hosted static PWA (HTTPS: GitHub Pages / dodonov.dev) | Chrome/Edge desktop, Android Chrome. **Not iOS Safari** (Bluefy app works) | NimBLE service |
| 2 | **HTTP/WebSocket over SoftAP** | served by the watch from LittleFS at `192.168.4.1` | everything incl. iOS | SoftAP + httpd + LittleFS + `vite build` into flash |

Same built bundle for 1 and 2; the adapter is chosen by `location.hostname === '192.168.4.1'` (or a
`?transport=` override).

## What the firmware already provides (reuse, don't duplicate)

- `firmware/src/gen/params_gen.h` (generated by `firmware/tools/gen_params.py presets/1.json`):
  - `struct Params` — 87 fields, plain POD: `int v`, `float`, `bool`, `uint32_t` colours (0xRRGGBB).
    `sizeof(Params)` ≈ 348 B (bools are 1 B each; compiler padding, **not packed**).
  - `PARAM_FIELDS[]` — `{name, type 'i'|'f'|'b'|'c', byte offset}` for every field. This is the single
    source of truth for **every** transport; name strings equal the sim's `Params` keys exactly.
- `firmware/src/display.cpp` owns the two 72-row strip buffers (`display_strip(i)`), the async DMA push
  (`display_push_strip_async` / `display_wait_all`) and the staged full-frame push (`display_push_rows`).
- `firmware/src/main.cpp`:
  - `setParam(name, valueString)` / `dumpParams()` (JSON text, identical to the sim's export format, so
    `p?` output can be pasted into the sim's Import) / `params = PRESET_DEFAULT`.
  - `handleLine(char*)` — the serial command parser (`p name=value`, `p?`, `p!`, `t HH:MM:SS`, `d<N>`,
    `s` status, `x` framebuffer dump, `b<n>`). **First refactor:** move it to `command.cpp` with an output
    sink (`void (*out)(const char*)`) so the same parser serves Serial, a BLE "command" characteristic and an
    HTTP `/cmd` endpoint. Params are applied instantly — the renderer reads `params` every frame; sprite
    glyphs re-scale lazily when their inputs change; palette/LUTs are rebuilt every frame anyway.
  - Clock is a software `double clockSec` (seconds since midnight). Replace by `settimeofday()` + `localtime`
    when `setTime` arrives (epoch + tz offset from the phone); keep `t HH:MM` as a shortcut.
- Board has no RTC battery and no user button other than **BOOT (GPIO0)** and RESET. BOOT is readable
  after boot (`pinMode(0, INPUT_PULLUP)`) → use **hold BOOT 3 s** to toggle SoftAP mode. Fallback: SoftAP
  for the first 5 min after power-on, idle timeout 5 min (AMOLED + Wi-Fi is the power-hungry combo).

## Hard constraint: internal RAM

After boot the liquid face leaves **≈ 175 KB of internal heap** free (was 92 KB until the Phase 1 bounce
buffers were removed, 2026-08-20). The two 72-row strip buffers (`display_strip(i)`, 2 × 77 KB,
`MALLOC_CAP_DMA | MALLOC_CAP_INTERNAL`) are the remaining big internal allocation.

- NimBLE needs roughly 35–50 KB internal, Wi-Fi SoftAP + lwIP + httpd roughly 60–90 KB, Bluedroid (the
  stock Arduino `BLEDevice`) far more. → **Use NimBLE-Arduino (h2zero, `lib_deps = h2zero/NimBLE-Arduino @ ^2.1`)**,
  never Bluedroid. Never run BLE and Wi-Fi simultaneously; SoftAP is a mode you enter (BLE off) and leave.
- 175 KB is enough for NimBLE without changes. For Wi-Fi, if `heap_caps_get_largest_free_block` gets
  tight, free a strip: options in order of preference
  1. **One strip buffer**: render hours → push (wait) → render minutes → push. Costs the render/DMA overlap,
     expect ~30 fps instead of 40 (render 18 ms + 2 × 3.5 ms DMA, no overlap). Simplest, do this first.
  2. Shrink the strips instead of dropping one: two 36-row strips (+77 KB total) and push each tube in two
     halves — render/DMA overlap survives at finer granularity, `renderTube` needs a row-window argument.
  3. The 257 KB `PsramCanvas` is in PSRAM, so it isn't the issue — leave it (it only serves the old
     faces and the `x` dump; `display_push_rows` stages it through the strips).
  The real fix is the incremental-rendering work in `KAIZEN.md` (frame skip + dirty-column push), after
  which full-width strips aren't needed at all — but that is deliberately scheduled after the companion.
- Check with `s` (prints `heap`) after init of each radio; if `heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL)`
  < 20 KB, expect Wi-Fi to fail to start silently.

## Transport 1 — GATT design (recommended wire format)

Keep Web Bluetooth's limits in mind: `readValue()` returns ≤ 512 B (long reads handled by the browser),
`writeValue()` ≤ 512 B (long/prepared writes — NimBLE supports them), notifications ≤ MTU−3 (Android
negotiates 247–517; Linux BlueZ often 517). A 2 KB JSON dump does **not** fit a read → send the struct
as a binary blob and ship the schema with the app.

Service `LW` (custom 128-bit UUID, e.g. `6c1b0001-...`), characteristics:

| char | props | payload |
|---|---|---|
| `params` | read / write | raw `Params` bytes (`memcpy`), ~348 B. Write = whole struct or `offset,len` patch (see below). Validate `v == PARAMS_VERSION` on write. |
| `patch` | write | `[u16 offset][u8 len][bytes…]` repeated — partial updates from a slider without re-sending 348 B on every `input` event (~20 B per tick, fine at 30 Hz). |
| `cmd` | write / notify | the text line protocol (`handleLine`); replies notified in ≤ 180 B chunks, last chunk terminated by `\n\x04`. Covers time, presets, status, anything new without a schema change. |
| `telemetry` | notify (5 Hz) | packed struct: `float fps, along, across, gyro, fillH, fillM; u32 heap; u16 battMv; u8 mode` |
| `schema` | read | `u32 crc32` of the generated schema JSON, so the app can detect a mismatch between the hosted bundle and the firmware and refuse/hide unknown fields. |

**Schema for the web side:** extend `gen_params.py` to also emit `sim/public/params-schema.json`:
`[{name, type, off, size}]` + `sizeof(Params)` + crc. Size/offsets must come from the **compiler**, not
Python guesses — cheapest is a tiny generated `schema_check.cpp` that `static_assert`s a few offsets and
`sizeof(Params)`, and let Python compute offsets with the same rules (4-byte align for int/float/u32, 1 for
bool, struct size rounded to 4). Lock it with the static_asserts; if they fire, fix the Python.

Time: `setTime` = `cmd` `"T <epoch_s> <tz_offset_min>"` → `settimeofday`, store tz offset in NVS.

Presets on device: NVS namespace `lw`, blob `cur` (_done 2026-08-21: autosave 2 s after the last write, `crc` = `PARAMS_SCHEMA_CRC` guards layout changes, `p!` erases_),
blobs `p0..p7` + `n0..n7` names. Commands `P list | P save <name> | P load <name> | P del <name>`.
`presets/*.json` in the repo stay the "factory" ones, baked in via `gen_params.py presets/1.json presets/calm.json …`.

Auto-reconnect: the app calls `navigator.bluetooth.getDevices()` (Chrome flag-free since M117 on desktop
and Android) and `device.watchAdvertisements()` → connect on the first advertisement. Advertise as
`LiquidWatch-XXXX` (last 2 MAC bytes) with the service UUID in the advertising data so `requestDevice`
can filter by service.

## Transport 2 — SoftAP

- `WiFi.softAP("LiquidWatch-XXXX")`, captive-portal DNS (`DNSServer` → 192.168.4.1) so phones pop the page.
- Server: `ESPAsyncWebServer` (mathieucarbou fork for core 3.x) or the IDF `esp_http_server`. Endpoints:
  `GET /api/params` (JSON via `dumpParams`), `POST /api/params` (JSON body → `setParam` per key),
  `POST /api/cmd` (line → reply), `WS /ws` (telemetry push + cmd). JSON here is fine — no 512 B limit.
- Static files: `vite build` in `sim/` → `firmware/data/` (gzip everything; the three digit PNGs are the
  only large assets). `board_build.filesystem = littlefs`, `pio run -t uploadfs`. The `spiffs` partition in
  `default_16MB.csv` is 3.4 MB at 0xC90000 — plenty.
- Mode switching: BOOT held 3 s → stop BLE, start AP, show a small "AP: LiquidWatch-XXXX / 192.168.4.1"
  overlay in the bridge zone (y 72..167 is unused — but the spec says keep it black; a 5-minute exception
  while in setup mode is acceptable, or print it in the serial log only). Idle timeout 5 min, BOOT again exits.

## Companion app structure

Start **inside `sim/`**, don't create a second app yet: the sim already has the canvas renderer, the
params UI, JSON import/export, autosave, and a Web Serial client (`sim/src/serial.ts`). Add
`sim/src/transport/{types,serial,ble,http}.ts` and a "Device" fieldset (connect/disconnect, status pill,
"push params live" toggle, "pull from device", "set time from this phone", preset list). The existing
panel then drives both the canvas and the watch — the "live mirror" UX falls out for free. Lit can come
later when extracting a lean `companion/` build (the sim's cuff/gloss overlays, lens smoothing, and IMU scope are dev-only
and shouldn't ship to the watch's flash); with Vite that's a second entry point, not a second repo.

Throttle: coalesce slider `input` events to ≤ 20 Hz per field, send `patch` (BLE) / `POST` (HTTP);
send full `params` on preset load/import.

## Where to start (recommendation)

1. **Transport 0 — Web Serial.** _Done 2026-08-21: `sim/src/transport/{types,serial}.ts`, Device fieldset
   in `main.ts` (connect, live push coalesced to ≤ 20 Hz, pull, push all, set time); `serial.ts` is the IMU
   feed on top of the transport. Verified on the board: write 26 ms, `p?` 15 ms._ `serial.ts` already owns the port; add a
   `write(line)` and push `p name=value` on every param edit (throttled), `p?` on connect to pull, `t` on
   "set time". This validates the whole UX loop (live mirror, throttling, pull/push semantics, the
   transport interface) with the board on the desk, before any radio/memory work. ~1–2 h.
2. **Firmware refactor:** `command.cpp` with output sink; `settimeofday` clock (_done_); NVS autosave of `params` (_done_);
   one-strip fallback behind a `#define` and measure fps. Still serial-only, still easy to test with
   `compare-device.py`.
3. **BLE (NimBLE)** with the characteristics above + the BLE adapter; host the sim build on GitHub Pages
   to get HTTPS for Web Bluetooth (localhost also counts as secure for dev).
4. **SoftAP + LittleFS** last — most memory, most moving parts, and it's only needed for iOS.

BLE before SoftAP because: it is the primary path on your own phone (Android), costs half the RAM, needs no
mode switching or captive portal, and the hosted-PWA deployment is one `vite build` + push.

## Gotchas collected so far

- WSL2 + browser on Windows: don't usbipd-attach the board to WSL. Keep it on Windows (Web Serial works),
  flash with `firmware/tools/flash-win.sh` (builds in WSL, flashes via Windows `python.exe -m esptool`, COM auto-detected
  by VID_303A). The port is exclusive: disconnect in the sim's Device fieldset before flashing.

- USB CDC: the board prints nothing unsolicited; commands are newline-terminated and echoed (since
  session 4). Don't run `compare-device.py` while a monitor holds the port.
- `Params` bools are 1 byte; a JS `DataView` writer must use the generated offsets, never assume 4-byte
  stride.
- The firmware applies params instantly with **no validation** (`p fizzCount=100000` would try to allocate
  fizz — capped at 64; `digitScaleY` > ~13 is clamped to a 96-row glyph; other fields are unchecked). Add
  min/max from the sim's `PARAM_META` to the schema and clamp on device before exposing this to strangers.
- `ImuFilter` state is not reset when filter params change — fine, it converges within a second.
- Web Bluetooth needs a user gesture for `requestDevice`; `getDevices()` + `watchAdvertisements()` does not.
- Android Chrome: keep the page in the foreground while writing; background tabs get GATT operations throttled.
